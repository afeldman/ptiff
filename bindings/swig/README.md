# SWIG binding for the libptiff C ABI (`bindings/swig`)

One SWIG interface file (`ptiff.i`) drives the **Go and Ruby** target languages
from the real C ABI header generated by the Rust core (`crates/ptiff-c`, via
cbindgen). The generated wrappers are plain C (no `-c++`), bound only to the
`extern "C"` surface of `libptiff_c`, so they carry **no C++ runtime, no C++
headers, no libstdc++** (confirmed with `otool -L`: only `libptiff_c`
linkage).

> **Octave is NOT built by SWIG anymore.** The Octave binding is now the
> hand-written C++ MEX adapter in [`bindings/octave/mex`](../octave/mex/),
> built with `mkoctfile` against the same C ABI (see [`bindings/octave/README.md`](../octave/README.md)).
> The old SWIG-Octave module (bindings/octave/lib + test/) was removed
> (see PTIFF-1.0-RUST-CORE-PLAN.md §10); `ptiff.i`/`typemaps.i` no longer carry
> an Octave target.

> **Place in the project — DECISION (2026-08-11).** SWIG is the **primary** binding
> surface. The maintainer has chosen *"alles in SWIG"*: the SWIG-generated
> modules **replace** the hand-written bindings (`bindings/go`,
> `bindings/python`, `bindings/ruby`) one language at a time.
> **Go is promoted** (2026-08-12): `bindings/go/ptiff` is now SWIG output,
> regenerated from this directory's `ptiff.i` by `make -C bindings/swig go`
> (see [`bindings/go/README.md`](../go/README.md)); the hand-written cgo
> wrapper is deleted. **Python is promoted** (2026-08-13): `bindings/python/src`
> is now SWIG output, regenerated by `make -C bindings/swig python`; the
> hand-written ctypes wrapper is deleted. **Ruby is promoted** (2026-08-13):
> `bindings/ruby/lib` is now SWIG output, regenerated by `make -C bindings/swig
> ruby`; the hand-written Fiddle wrapper is deleted. **Octave is promoted**
> (2026-08-14): `bindings/octave/lib` is now SWIG output, regenerated by
> `make -C bindings/swig octave`; the hand-written Octave wrapper is deleted.
> **All four SWIG targets are now promoted** — `bindings/swig` itself no longer
> holds any staged per-language output.
> **Rust has no SWIG target** — the Rust core *is* the C ABI (crates/ptiff-c
> exposes `extern "C"`; cbindgen authorises `target/ptiff_c.h`). See
> ["Planned migration"](#planned-migration) below.

> **Status of this file.** Tracked work for `bindings/swig` is coordinated in the
> `todo` tool / commit messages. This README is living documentation; the
> "Planned migration" section records the agreed direction (now executed).

## Why the shim include dir (`real_inc/`)

SWIG parses headers with its own C preprocessor, and the Rust/cbindgen header
`target/ptiff_c.h` expands `PTIFF_C_API` to
`__attribute__((visibility("default")))` on GCC/clang — which SWIG cannot parse.
The build therefore creates **`real_inc/`** as a **sed-filtered copy** of
`target/ptiff_c.h`: the `sed` strips the `#if defined(_WIN32)...` `PTIFF_C_API`
macro block, so in `real_inc/ptiff_c.h` `PTIFF_C_API` expands to nothing.

SWIG parses against `real_inc/` (`-I real_inc`); the C-compiled wrapper still
uses the **real** Rust-generated header via the `%{ ... %}` block (emitted
verbatim into the generated wrapper), so struct layouts and prototypes come from
the authoritative cbindgen source. `real_inc/` is a reproducible build
artifact — `make` regenerates it from `target/ptiff_c.h`, and it is gitignored
(no export-header shim anymore: since 2026-08-24 the cbindgen header is the ABI
source of truth and there is no separate `swig_include/ptiff_c_export.h`).

## Why typemaps are language-specific

SWIG typemaps are **not** portable across languages: a Python `Py_buffer`
typemap has no meaning to Go or Ruby. Each language needs its own mapping of the
C ABI's counted `(ptr, size)` buffers and `size_t*`/`int*` out-params. In
`typemaps.i` the four are selected by the SWIG-provided preprocessor macros
(`SWIGPYTHON`, `SWIGGO`, `SWIGRUBY`, `SWIGOCTAVE`), which are always defined for
the matching target. The Rust ABI uses `uintptr_t` buffers (Rust `usize`) and
`int32_t` out-params (Rust `i32`), so the typemaps are matched on those concrete
types:

- **Python** — write buffers collapse onto a readable buffer (`bytes`/`bytearray`/
  `memoryview`); read buffers onto a **writable** one (`PyBUF_WRITABLE`);
  `int32_t *err_out` / `uintptr_t *bytes_read` become extra return values.
- **Go** — `(ptr, size)` pairs collapse onto `[]byte` (mirrors SWIG's own
  `go/cdata.i`: the C wrapper pulls `.array`/`.len` off the Go slice); out-params
  stay in/out pointers (`*int`, `*int64`) matching Go's return-by-pointer idiom.
- **Ruby** — buffers collapse onto a `String` (`RSTRING_PTR`/`RSTRING_LEN`);
  out-params become extra return values (`SWIG_Ruby_AppendOutput`).
- **Octave** — buffers accept a `uint8` (row) array or a `String`; read
  buffers are returned back as an extra `uint8` output value (Octave arrays
  are copy-on-assign, so there is no in-place mutation); out-params become
  extra return values (`SWIG_Octave_AppendOutput`).

So per-language the call surface is:

```python
res = ptiff.ptiff_source_open(OUT)   # -> [handle, err_out]
rc, n = ptiff.ptiff_source_read_tile(src, 1, 0, buf)  # buf: writable bytearray
```

```go
src := Ptiff_source_open(out, &errOut)                 // handle; errOut via ptr
rc := Ptiff_source_read_tile(src, 1, 0, buf, &nread)   // buf: []byte filled in place
```

```ruby
res  = Ptiff::ptiff_source_open(OUT)                   # -> [handle, err_out]
res2 = Ptiff::ptiff_source_read_tile(src, 1, 0, buf)   # -> [rc, bytes_read]; buf: String
```

```octave
[src, ~]   = ptiff_source_open(OUT);                   % handle + int err_out
[rc, d, n] = ptiff_source_read_tile(src, 1, 0, uint8(zeros(1, bs)));  % d: uint8 data
```

## Building and testing

Requires `swig` (≥4.x), the **Rust-built** `libptiff_c` in the workspace
`target/release/`, plus the target toolchains (`go`, `ruby`). The Octave
binding is built separately via its own MEX Makefile
(`make -C bindings/octave/mex build`), so this SWIG Makefile needs no
Octave/mkoctfile. No pkg-config and no CMake are involved — the Makefile links
straight against the Rust output.

```bash
# build the Rust C ABI once (from the repo root): cbindgen emits the header
# to target/ptiff_c.h and Cargo builds the lib into target/release/
cargo build -p ptiff-c --release

# build + run the Go + Ruby round-trip + feature test suites
cd bindings/swig
make test
```

Useful targets:

- `make` — build both (Go module, Ruby bundle)
- `make go` / `make ruby` — build one language
- `make staticlib` — ensure `libptiff_c` exists (runs
  `cargo build -p ptiff-c --release` if the lib is missing from `target/release`)
- `make test` — build all, then run both test suites
- `make clean` — remove generated outputs

The `make go` target also scaffolds `go/go.mod` (module
`github.com/crater/ptiff-go`) and `go/cgo_flags.go` (a `#cgo CFLAGS: -I`
directive pointing at `target/` and a `#cgo LDFLAGS: -L -lptiff_c -Wl,-rpath`
directive pointing at `target/release/` — direct paths, no pkg-config) so plain
`go test ./...` in `go/` works without extra flags.

## Status

The Go and Ruby round-trip tests round-trip a 32×32 UInt8 image tiled 16×16
(write via `ptiff_sink_*`, read via `ptiff_source_*`). (The Octave binding,
being the separate MEX adapter, has its own test suite under
`bindings/octave/mex/`.) Known SWIG output notes:

- Go handles are raw value structs wrapping a `uintptr`; close each `sink`/`source`
  **once** (no defer + explicit double-close — it frees the C pointer).
- SWIG Go does not support the `%apply ... OUTPUT` grouping, so `err_out` /
  `bytes_read` stay pointer out-params (idiomatic Go).
- Ruby normalizes `ptiff_version` → `Ptiff_version` etc. (SWIG Warning 801).
- `%nodefaultctor`/`%nodefaultdtor` keep `ptiff_source`/`ptiff_sink` non-constructible.
- SWIG 4.5.0's generated Python shadow-class `__init__` (`SWIG_Python_InitShadowInstance`)
  segfaults on CPython 3.14 (confirmed locally); build against 3.13 or earlier
  (`PYTHON=$(uv run --project ../python python)` picks up the project's pinned
  interpreter — see `.github/workflows/python-bindings.yml`). Not yet reported
  upstream.

## Planned migration — "alles in SWIG"

> **COMPLETED (2026-08-24).** The migration described in this section is now
> **complete**. As of 2026-08-24 the SWIG stack builds the **Rust-generated** C
> ABI: the old hand-written `bindings/c/` has been **deleted entirely**, the
> `bindings/swig/swig_include/` export-header shim has been **deleted**, the C
> header comes from **`crates/ptiff-c`** (cbindgen emits `target/ptiff_c.h`;
> SWIG parses the sed-filtered `real_inc/ptiff_c.h`), and `libptiff_c` is built
> by **Cargo** into `target/release/`. The historical bullet log below is kept
> for reference; it records the direction agreed on 2026-08-11 and each step as
> it landed, but it should no longer be read as "pending" work.

Agreed direction (with user, 2026-08-11): **SWIG becomes the single, primary
binding layer** for the languages it targets. The hand-written bindings
(`bindings/go`, `bindings/python`, `bindings/ruby`) were **replaced** by SWIG
outputs and removed. This section records the scope and acceptance criteria (now
satisfied).

### Scope

- Replace the **Python, Go, Ruby** bindings with the SWIG-generated modules in
  this directory (promoted to the official language bindings); **Octave** was
  added as a fourth SWIG target.
- **Rust is out of scope** — there is no SWIG Rust target; the Rust core
  implements the C ABI itself (crates/ptiff-c, via cbindgen).
- New languages SWIG supports (Java, C#, Lua, Perl, PHP, R, Tcl, ...) can be
  added cheaply from `ptiff.i` as a side benefit of the C-ABI-first approach,
  but are not part of this first migration.

### Why (rationale)

- One `ptiff.i` + one per-language typemap set replaces three independently
  maintained hand-written wrappers: **one maintenance path** for three
  languages, all covering the full C ABI surface. (Octave brings a fourth.)
- The C ABI (generated by the Rust core, `crates/ptiff-c` → cbindgen →
  `libptiff_c`) remains the single source of truth.
- SWIG (pure C mode) carries **no C++ runtime** — same guarantee as the
  hand-written C-ABI bindings.

### What must not regress (acceptance criteria)

The hand-written bindings already cover more than the current round-trip tests.
Before replacing/removing them, the SWIG modules must reach **at least parity**
with what they test, so nothing is lost:

- **Go** (`bindings/go/ptiff`): no longer just tile round-trip — version,
  logger, backend registry, error codes, `Image`/`ImageDescriptor`, sink/source
  with proper close-once semantics.
- **Python** (`bindings/python`): version/logger/image/backends features (the
  Cucumber `features/*.feature` suite) plus the ctypes unit tests.
- **Ruby** (`bindings/ruby`): version + tile round-trip tests.
- **Octave** (`bindings/octave`): version, logger, backend, error fields,
  image and sink tests over the SWIG output.

## Octave removed from SWIG (2026-08-24)

**Octave is no longer a SWIG target.** After the initial SWIG-Octave promotion,
the binding was consolidated onto the hand-written C++ MEX adapter
(`bindings/octave/mex/`), which calls the same C ABI directly — it is more
maintainable and idiomatic for Octave than the generated SWIG module. The old
`bindings/octave/lib/` (SWIG output) and `bindings/octave/test/` (SWIG-driven
suite) were **deleted**, and this Makefile's `octave` target, `OC_DIR`,
`MKOCTFILE`/`OCTAVE`, and the Octave test invocation were **removed**. The
historical "Octave is promoted / fourth SWIG target" notes above record the
(now superseded) earlier state. Build/test the Octave binding with:

```bash
make -C bindings/octave/mex build
make -C bindings/octave/mex test
```

The `SWIGOCTAVE` typemaps in `typemaps.i` are harmless leftovers (guarded by a
macro SWIG never defines for the Go/Ruby targets) and can be dropped in a later
cleanup pass.
